## HTML over HTTP

A page is a response: **`Content-Type: text/html; charset=utf-8`**, a status code that browsers and crawlers act on (**200**; redirects **301/308** permanent, **302/307** temporary, **303** "go GET this"; **404** with a helpful page; **410** gone; **500**), **`Cache-Control`** (HTML short and revalidated, hashed assets long and `immutable`), `Content-Language`, `Link` headers for preloading, **103 Early Hints** (send preload hints before the page is ready), and **streaming** (send the `<head>` and shell immediately, flush the rest as data arrives).

## Forms as the original API

The server receives `application/x-www-form-urlencoded` or `multipart/form-data`. **POST → Redirect → GET** (303) prevents resubmission on refresh. **Server-side validation** re-renders the form with the user's values, inline errors and an error summary (Part 3's accessible pattern, now server-generated) with status **422**. **CSRF tokens** in hidden inputs, checked against the session. Idempotency keys and double-submit protection. File uploads: size limits, type checking **by content, not extension**, storage outside the web root, signed direct uploads. HTML only has GET and POST, so other verbs use method-override conventions (a proposal to add more is **[Frontier]**).

<Try task="In the server lab above: submit empty, then with an invalid email, then valid data; then tick 'Forge the CSRF token' and submit again. Write down the status code of each response and what the browser did next.">
  Empty: 422, the same page with an error summary (focus moves to it) and each field marked `aria-invalid`. Invalid email: 422 with only the email error, and your other values preserved. Valid: 303 with `Location: /contact/thanks`, then the browser's automatic GET → 200. Forged token: 403 Forbidden, nothing stored. With PRG off, the valid POST returns 200 directly, and Refresh re-sends it, storing a duplicate.

## Templating and auto-escaping

Server template languages (Jinja/Nunjucks, Liquid, Handlebars/Mustache, EJS, ERB, Blade, Go `html/template`, Razor, Twig, JSX rendered on the server) share the same parts: **auto-escaping**, layouts and blocks, partials/includes, components/macros, loops and conditionals. Keep logic out of templates. And know the **contexts**: auto-escaping covers HTML text and quoted attributes; URLs, scripts and CSS need their own encoding or validation. (Go's `html/template` is one of the few that escapes by context automatically.)

<EscapeLab />

```ts
// The whole idea of auto-escaping in 20 lines (this site's lib/html-template.ts)
const SAFE = Symbol('safe-html');
export const raw = (value: string) => ({ [SAFE]: true, value });        // a hole you cut on purpose
export function html(strings: TemplateStringsArray, ...values: unknown[]) {
  let out = strings[0] ?? '';
  values.forEach((v, i) => {
    out += (v && typeof v === 'object' && SAFE in v) ? v.value          // nested templates stay as-is
         : Array.isArray(v) ? v.map(String).join('')
         : escapeHtml(String(v ?? ''));                                  // everything else is escaped
    out += strings[i + 1] ?? '';
  });
  return raw(out);
}
```

## Hypermedia-driven applications

**HTML over the wire** as an architecture: the server sends HTML with the next actions embedded (HATEOAS). **htmx** (`hx-get`, `hx-post`, `hx-target`, `hx-swap`, `hx-trigger`, `hx-boost`, out-of-band swaps), **Hotwire/Turbo** (Drive, Frames, Streams), Datastar and Unpoly. Great for CRUD apps and dashboards; weaker for highly interactive client-state apps (Carson Gross, *Hypermedia Systems*).

## Server-rendered components

**Declarative Shadow DOM** (Part 20) lets web components render on the server; **React Server Components** emit HTML (and a serialised tree) from the server; **islands** architecture hydrates only the interactive parts (Astro, Fresh); **partial hydration** ships JavaScript per component. With SSR come markup obligations: **valid nesting** (or the parser rewrites it and hydration fails), **stable IDs** (no `Math.random()`), and **deterministic output** (no server/client differences in dates or locales).

```astro
---
// An Astro page: rendered to HTML at build time. Only the island ships JavaScript.
import Header from '../components/Header.astro';     // static HTML, zero JS
import CartButton from '../components/CartButton.tsx'; // interactive island
---
<Header />
<main>
  <h1>Trail Runner 3</h1>
  <CartButton client:visible productId="tr3" />  <!-- hydrated only when scrolled into view -->
</main>
```

## Sanitising user HTML

Never render user-submitted HTML unsanitised. Use **allowlist** sanitisers: DOMPurify in the browser, `sanitize-html` or bleach on the server, and the browser's **Sanitizer API** (`element.setHTML()`) **[Frontier]**. Prefer **Markdown** for user content with raw HTML disabled or sanitised, and mark user links **`rel="ugc nofollow"`**.

## Error and edge pages

404, 500, maintenance, offline (service worker), rate-limited (429 with `Retry-After`), and "JavaScript failed" states, **all designed as carefully as the home page**: say what happened in plain words, offer the next step (search, home, the likely page), keep the site's navigation, return the **correct status code** (a "not found" page served with 200 is a soft 404 that search engines index), and never leak stack traces.

<Try task="Visit /definitely-missing on this site. Evaluate the 404 page: status code (check the Network panel), wording, next steps, navigation. Then design the 500 and 429 equivalents.">
  This site's 404 keeps the header and navigation, says plainly the page doesn't exist, and links to the index of all parts and the home page; on a static host it's served with a real 404 status. A 500 page should apologise without blaming, avoid technical details, offer a retry and a status page link, and be static (it must render when the app is broken). A 429 should say when to try again (and send `Retry-After`).
</Try>
