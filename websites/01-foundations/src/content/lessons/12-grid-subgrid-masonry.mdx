## The model: tracks first, then placement

Grid is **two-dimensional**. The container defines **tracks** (rows and columns); tracks are separated by numbered **lines**; the intersection of a row and column is a **cell**; a rectangle of cells is an **area**. Items are **placed** onto that structure, automatically (auto-placement fills cells in order) or explicitly.

## Track sizing and the `1fr` trap

Tracks take fixed lengths, percentages, **`fr`** (a share of the *remaining* space), `auto`, `min-content`, `max-content`, `fit-content()`, **`minmax(min, max)`** and `repeat()`. The trap: **`1fr` means `minmax(auto, 1fr)`**, and `auto` is the content's min-content size, so a long URL or code block blows the column out. The fix is **`minmax(0, 1fr)`**.

## Responsive without media queries: auto-fill vs auto-fit

`repeat(auto-fill, minmax(min(100%, 16rem), 1fr))` creates as many columns as fit, each at least 16rem. **`auto-fill`** keeps empty tracks; **`auto-fit`** collapses them so the items stretch. The **`min(100%, 16rem)`** guard stops a single column overflowing on screens narrower than 16rem.

<Playground
  id="p12-autofit"
  title="auto-fill keeps empty tracks; auto-fit collapses them"

  html={`<p>auto-fill</p><div class="fill"><div>1</div><div>2</div></div>\n<p>auto-fit</p><div class="fit"><div>1</div><div>2</div></div>`}
  css={`.fill, .fit { display: grid; gap: .5rem; outline: 2px dashed #999; }\n.fill { grid-template-columns: repeat(auto-fill, minmax(min(100%, 7rem), 1fr)); }\n.fit { grid-template-columns: repeat(auto-fit, minmax(min(100%, 7rem), 1fr)); }\n.fill > div, .fit > div { background: #fed7aa; padding: .5rem; }`}

## Placement: lines, spans, names and areas

Place with **line numbers** (negative numbers count from the end, so `1 / -1` spans everything), **`span n`**, **named lines** (`[content-start]`), and **`grid-template-areas`**: ASCII-art layouts that double as documentation, with `grid-area: name` on the items. Items beyond the explicit grid create **implicit tracks** sized by `grid-auto-rows`/`grid-auto-columns`. **`grid-auto-flow`** chooses `row` or `column` filling, and `dense` back-fills holes at the cost of reading order.

<Playground
  id="p12-areas"
  title="grid-template-areas as a readable layout"

  html={`<div class="page"><header>Header</header><nav>Nav</nav><main>Main</main><aside>Aside</aside><footer>Footer</footer></div>`}
  css={`.page { display: grid; gap: .5rem; min-height: 16rem;\n  grid-template-columns: 8rem minmax(0, 1fr) 8rem;\n  grid-template-rows: auto 1fr auto;\n  grid-template-areas:\n    "header header header"\n    "nav    main   aside"\n    "footer footer footer"; }\nheader { grid-area: header; } nav { grid-area: nav; } main { grid-area: main; } aside { grid-area: aside; } footer { grid-area: footer; }\n.page > * { background: #fed7aa; padding: .5rem; }`}

## Overlap and layering

Several items can occupy the **same cell**: hero text over an image without `position: absolute`, so the container still sizes to the taller of the two. `z-index` works on grid items without positioning. The **stack** pattern names one area and puts every layer in it.

## Alignment in two dimensions

Per item: `justify-self` (inline axis) and `align-self` (block axis), or both with `place-self`. For all items: `justify-items`, `align-items`, `place-items`. For the whole grid inside a larger container: `justify-content`, `align-content`. Spacing: `gap`.

## Subgrid

`grid-template-columns: subgrid` or `grid-template-rows: subgrid` lets a nested grid **borrow its parent's tracks**, so separate components align with each other: card headers, bodies and footers aligned across a row of cards; form labels and inputs aligned across fieldsets. Line names are inherited, and gaps can be overridden in the subgrid.

## The full-bleed layout

Named lines turn a page into three nested widths: `[full-start] minmax(1rem, 1fr) [content-start] minmax(0, 65ch) [content-end] minmax(1rem, 1fr) [full-end]`. Every child sits in `content` by default; any child can **break out** with `grid-column: full`. It's the modern layout for articles and marketing pages, and it's how this site's pages are built (with an extra `wide` track).

## The grid sizing algorithm

In order: **resolve intrinsic track sizes** (first for items spanning one track, then for items spanning several, distributing their extra size across the spanned tracks), **maximise** tracks up to their growth limits, **expand flexible (`fr`) tracks** with the leftover space, then **stretch `auto` tracks**. Percentages and intrinsic sizes interact surprisingly: a percentage track in an auto-sized grid resolves against a size that doesn't exist yet, so it behaves as `auto` during sizing and then resolves.

## Masonry **[Frontier]**

A masonry layout packs items of different heights into columns without row alignment. The specification debated whether it belongs in grid (`grid-template-rows: masonry`) or needs its own display type, and has resolved toward **grid lanes** (`display: grid-lanes`). Check what has shipped where before relying on it. Fallbacks today: **CSS columns** for simple cases (but items flow top-to-bottom, then across), grid with `dense` for approximations, or JavaScript for true masonry.

## Grid for pages and for components

**Macro layout**: page shells via named areas. **Component internals**: a card's image/title/meta, a form row's label/input/hint, a dashboard tile. **Design grids**: translate a 12-column Figma grid into CSS with named lines (`[col-1-start] … [col-12-end]` or `repeat(12, [col-start] minmax(0, 1fr))`) instead of utility classes, so components say `grid-column: col-start 3 / span 6`.

## Grid inspection

Firefox and Chrome DevTools draw grid overlays: line numbers (positive and negative), line names, area names, track sizes and gaps. Firefox's is the most detailed; Chrome's shows subgrid and flex overlays too. Use them constantly: most grid bugs are visible in one glance at the overlay.

## Accessibility: placement is presentation

Grid placement (line numbers, areas, `order`, `dense`) moves boxes visually but **doesn't change reading or focus order**. Keep the DOM in a meaningful order and use placement for presentation only; if the visual order must differ, check it with a keyboard and a screen reader.
