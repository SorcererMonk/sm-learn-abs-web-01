## Why CSS gets hard at scale

A **global namespace**, **specificity escalation** (each fix a little more specific than the last), **ordering dependencies** (it works because this file loads later), **dead code** nobody dares delete, **inconsistent values** ("47 shades of grey") and components that **break when moved**. Every methodology answers some subset of these.

## Methodologies, and what survives

**OOCSS** (separate structure from skin, container from content), **SMACSS** (base, layout, module, state, theme), **BEM** (`block__element--modifier`: flat specificity through naming), **ITCSS** (an inverted triangle ordered by specificity and reach: settings → tools → generic → elements → objects → components → utilities, the ancestor of `@layer`), SUIT CSS, **Atomic/Functional CSS**, and **CUBE CSS** (Composition, Utility, Block, Exception: embrace the cascade, use layout primitives, keep blocks small). What survives: flat specificity, ordering by reach, layout primitives, and small components.

## Utility-first CSS

**Tailwind's model**: atomic classes composed in markup, a token-driven scale, unused styles removed at build, and in v4 a CSS-first config (`@theme`) with native cascade layers. Trade-offs: co-location and consistency vs verbose markup and abstraction pushed into components. `@apply` is usually a smell (you've recreated a component class). A core skill: **reading Tailwind as CSS**.

```html
<!-- Tailwind -->
<button class="inline-flex items-center gap-2 rounded-lg bg-orange-700 px-4 py-2 font-semibold text-white hover:bg-orange-800 focus-visible:outline-2 focus-visible:outline-offset-2 disabled:opacity-50">
  Save
</button>
```

```css
/* The same, read as CSS */
.button {
  display: inline-flex; align-items: center; gap: .5rem;
  border-radius: .5rem; background: var(--color-orange-700);
  padding: .5rem 1rem; font-weight: 600; color: white;
}
.button:hover { background: var(--color-orange-800); }
.button:focus-visible { outline: 2px solid; outline-offset: 2px; }
.button:disabled { opacity: .5; }
```

## Scoping approaches

Naming conventions (BEM); **CSS Modules** (build-time hashed class names); **runtime CSS-in-JS** (styled-components, Emotion: flexible, with runtime cost and Server Component friction) vs **zero-runtime** (vanilla-extract, Linaria, Panda CSS, StyleX: typed and extracted at build time); framework-scoped styles (Vue, Svelte, **Astro**: this site's demos use Astro's scoped styles); **shadow DOM**; and native **`@scope`**. Choose by team, framework and performance needs.

## Preprocessors and postprocessors

**Sass** is still widely used (modules with `@use`, mixins, functions, maps), though much of it is native now (variables → custom properties, nesting, `color-mix()`, math functions). Less is legacy. **PostCSS** runs plugins (autoprefixer, custom transforms). **Lightning CSS** transforms, minifies and lowers modern syntax for older browsers, fast. Decide what still needs a build step: often only bundling, minification and syntax lowering.

```scss
// Sass that native CSS now covers
$brand: #c2410c;                          // → --brand: #c2410c;
.card { &:hover { color: darken($brand, 10%); } }   // → nesting + oklch(from var(--brand) calc(l - .1) c h)
@mixin stack($space) { > * + * { margin-top: $space; } }  // → a .stack class with --space
.grid { width: math.div(100%, 3); }       // → calc(100% / 3)
// Still Sass-only: loops generating many classes, maps, compile-time functions
```

<Try task="Take a Sass file you know (or any open-source one) and mark each feature as 'native now', 'native soon' or 'still needs Sass'.">
  Variables, nesting, colour functions and arithmetic are native now. Mixins are partly native via custom properties and `@function` **[Frontier]** for values; loops (`@each` generating utility classes) and maps still need Sass or a script. Most modern codebases keep a build step only for bundling, minification, and lowering new syntax for older browsers (Lightning CSS).
</Try>

## The modern native architecture

Zero dependencies: **`@layer`** for ordering (reset, tokens, base, layout primitives, components, utilities, overrides), **custom properties** for tokens and component APIs, **`@scope`** or conventions for component boundaries, **nesting** for readability, **container queries** for component responsiveness, and **`:where()`** for low-specificity defaults. This site is built this way: `@layer reset, tokens, base, layout, components, motion, site, demos, print`.

## Design tokens

Design decisions as **data**: colour, type, space, radius, shadow, motion, z-index, breakpoints. **Tiers**: primitive/reference tokens (`blue-600`) → semantic/system tokens (`color-action-primary`) → component tokens (`button-bg`). The **W3C Design Tokens Community Group format** (JSON with `$value`, `$type` and `{aliases}`). Pipelines (**Style Dictionary**, Tokens Studio, Figma variables export) turn tokens into CSS custom properties, iOS and Android constants, per mode (light/dark, brands, density). ## Theming

Swap tokens per `[data-theme]` or a `:root` class; **`light-dark()`** for colour schemes; multi-brand white-labelling (a different primitive set behind the same semantic names); **user-customisable themes** (an accent picker feeding relative colour); **density modes** (compact/comfortable); and no flash of the wrong theme (a blocking inline script reading a cookie or localStorage before first paint, as this site does).

## Component API design in CSS

Variants (`data-variant`, classes or props), sizes, **states driven by ARIA attributes and pseudo-classes**, **custom properties as the public styling API** (`--button-padding`), sensible defaults via `:where()`, composition over configuration, slots for content, and resilience rules: no fixed heights, no magic numbers, logical properties, intrinsic sizing.

## Design systems as products

**Foundations** (tokens, type, colour, grid, motion, iconography), **components**, **patterns** (forms, navigation, empty states), content guidelines, **accessibility guarantees per component**, documentation (Storybook, Zeroheight, custom docs sites), contribution and governance models, versioning and deprecation, adoption metrics, and **design–code parity** (Figma components mirrored by code components, Code Connect).

<Try task="Write a one-page component spec for a Toast: purpose, anatomy, variants, states, tokens used, accessibility guarantees, do/don't, and its version and deprecation policy.">
  Purpose: brief, non-blocking status after an action. Anatomy: icon, message, optional action, close. Variants: info, success, error. States: entering, visible, paused on hover/focus, exiting. Tokens: `toast.bg`, `toast.radius`, motion `enter`/`exit`. Accessibility: rendered into a pre-existing `role="status"` region (errors: `role="alert"`), never auto-dismissed while focused, at least 5 s, dismissible by keyboard, no essential info only in a toast. Don't: stack more than 3, use for errors that need action. Versioning: semver, deprecated props warned for one minor version.
</Try>

## Headless and composable UI

**Headless behaviour libraries** (Radix Primitives, React Aria, Ark UI, Headless UI, Base UI) provide keyboard, focus and ARIA behaviour while you own the styling. The **shadcn/ui model** copies component source into your codebase so you own it. Choose between a full component library (fast, generic look), a headless library (behaviour solved, look yours) and building on native elements (smallest, when the platform covers it).

<Try task="For each of these, choose native, headless or full library, and justify: a date picker, a combobox with async search, a disclosure, a modal dialog, a data grid with virtualisation.">
  Date picker: headless (React Aria's calendar) unless `<input type="date">` is acceptable. Async combobox: headless (hard keyboard and ARIA contract). Disclosure: native `<details>`. Modal: native `<dialog>` with `showModal()`. Data grid with virtualisation: a full library (TanStack Table + a virtualiser, or AG Grid): behaviour and performance are the product.
</Try>

## Styling in frameworks

**JSX** differences (`className`, `htmlFor`, style objects with camelCase and numbers as px, boolean attributes); **React 19** stylesheet precedence and hoisting (`<link rel="stylesheet" precedence="default">`); Vue and Svelte scoped styles and `:global`; **Astro's** scoped styles and islands (this site); and Server Components' preference for static, extractable CSS over runtime CSS-in-JS.

```tsx
// React 19: the stylesheet is hoisted into <head>, deduplicated and ordered by precedence
export function Chart() {
  return (
    <>
      <link rel="stylesheet" href="/chart.css" precedence="default" />
      <figure className="chart" style={{ '--bars': 12, aspectRatio: '16 / 9' } as React.CSSProperties}>
        <label htmlFor="range">Range</label>
        <input id="range" type="range" disabled={false} />
      </figure>
    </>
  );
}
```
