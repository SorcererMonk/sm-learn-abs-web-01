## The form as a protocol

A `<form>` is a declarative HTTP request. `action` is the URL, `method` the verb and `enctype` the body format. **GET** puts the fields in the query string: idempotent, bookmarkable, right for search and filters. **POST** puts them in the body and is right for anything that changes state. `application/x-www-form-urlencoded` is the default body; `multipart/form-data` is required for files; `text/plain` is for debugging only.

What gets sent is precise. Only **successful controls with a `name`** are submitted. Disabled controls are skipped (use `readonly` if you need the value sent), unchecked checkboxes and radios send nothing, and the **submitter button's** own `name=value` is included, so two buttons can mean two actions. A button can override the form with `formaction`, `formmethod`, `formenctype` and `formnovalidate`. A control outside the element joins a form with `form="form-id"`. All of this works with **no JavaScript at all**.

## Every input type and what it buys you

The `type` attribute chooses the mobile keyboard, the autofill heuristics, built-in validation, the native picker and the accessibility role, all at once. `email` and `url` validate format and bring the `@` and `.com` keys; `tel` brings the phone pad without validating (phone formats vary too much); `search` adds a clear button and the `searchbox` role; `date`, `time`, `datetime-local`, `month` and `week` bring native pickers; `color` and `range` bring their widgets; `file` takes `accept`, `multiple` and `capture`.

**`type="number"` is for quantities**, not for things that are merely digits. Card numbers, PINs, one-time codes and postcodes are identifiers: use `type="text"` with **`inputmode="numeric"`**, which gives the numeric keyboard without spinners, scroll-wheel changes or dropped leading zeros.

## Labels, groups and the other form elements

A `<label>` gives a control its **accessible name** and a bigger click target. Associate it explicitly (`for` matching `id`) or implicitly by wrapping. `<fieldset>` + `<legend>` names a group: radio groups, address blocks, "Date of birth". `<fieldset disabled>` disables everything inside at once.

The rest of the toolkit: `<select>` with `<option>`/`<optgroup>` (and `multiple`), `<textarea>` (with **`field-sizing: content`** it grows with its text), `<datalist>` for suggestions that still allow free text, `<output for>` for calculated results, `<meter>` for a gauge within a known range (disk usage, password strength) versus `<progress>` for task completion (indeterminate when it has no value). And the classic bug: **`<button>` defaults to `type="submit"`**, so a "Show password" button inside a form submits it.

## Autofill and `autocomplete` tokens

`autocomplete` tokens tell browsers and password managers what each field *is*: `name`, `given-name`, `family-name`, `email`, `tel`, `street-address`, `address-line1`, `address-level2` (city), `postal-code`, `country`, `cc-name`, `cc-number`, `cc-exp`, `cc-csc`, `one-time-code`, `username`, `current-password`, `new-password`, `webauthn`. Prefix with **`shipping`** or **`billing`**, and with `section-*` to separate two addresses on one page. It is the single biggest improvement to form completion rates, and **WCAG 1.3.5 Identify Input Purpose** requires it for fields about the user.

```html
<form action="/checkout" method="post">
  <fieldset>
    <legend>Shipping address</legend>
    <label for="n">Full name</label>
    <input id="n" name="name" autocomplete="shipping name" required>
    <label for="a">Address</label>
    <textarea id="a" name="address" autocomplete="shipping street-address" required></textarea>
    <label for="c">City</label>
    <input id="c" name="city" autocomplete="shipping address-level2" required>
    <label for="p">Postcode</label>
    <input id="p" name="postcode" autocomplete="shipping postal-code" required>
  </fieldset>
  <label for="u">Email</label>
  <input id="u" name="email" type="email" autocomplete="email" required>
  <label for="pw">Create a password</label>
  <input id="pw" name="password" type="password" autocomplete="new-password" minlength="12" required>
  <button>Continue to payment</button>
</form>
```

## Constraint validation

The browser validates before submit using attributes: `required`, `pattern` (anchored automatically), `min`/`max`/`step`, `minlength`/`maxlength`, and the type itself (`email`, `url`). The **Constraint Validation API** exposes it: `el.validity` (flags like `valueMissing`, `typeMismatch`, `patternMismatch`), `checkValidity()`, `reportValidity()` and `setCustomValidity(message)` for rules HTML can't express, such as "passwords match". Add `novalidate` to the form to keep the API but draw your own UI.

Styling hooks: `:invalid`/`:valid` match immediately (so empty required fields are red on load), while **`:user-invalid`** and `:user-valid` match only after the user has interacted, which fixes "red before typing". Also `:required`, `:optional`, `:placeholder-shown`, `:in-range`/`:out-of-range`. And **client validation is UX, not security**: the server validates again (Part 22).

## Accessible form patterns

- **Visible labels** always. A placeholder is not a label: it disappears on typing, often fails contrast, and is not reliably announced.
- **Hints** below the label, linked with `aria-describedby`, so they are read with the field.
- **Required** stated in text ("required" or "optional"), not only by colour or an asterisk.
- **Inline errors** next to the field, linked with `aria-describedby` (or `aria-errormessage`), and `aria-invalid="true"` on the field.
- An **error summary** at the top on submit: a heading, a list of links to each field, and focus moved to the summary.
- **Don't disable submit buttons**: people can't discover why. Let them submit and explain what's wrong.
- Sensible tab order (DOM order), grouping with fieldsets, **one question per page** for complex flows (the GOV.UK pattern), and **no redundant entry** (WCAG 3.3.7: don't ask for the same information twice in one process).

## Native interactive elements

The platform now ships the components teams used to hand-build. Each one comes with keyboard support, focus management and accessibility semantics.

### `<details>` and `<summary>`

A disclosure with no JavaScript: the `open` attribute reflects state, a shared **`name`** makes a group *exclusive* (an accordion where opening one closes the others), `::marker` styles the triangle and **`::details-content`** styles (and animates) the panel. Find-in-page opens a closed `<details>` when it contains the match.

### `<dialog>`

`show()` opens a non-modal dialog; **`showModal()`** puts it in the **top layer** (above every z-index), draws `::backdrop`, makes the rest of the page **inert**, moves focus inside and lets Escape close it. A `<form method="dialog">` closes the dialog and sets `dialog.returnValue` to the submitter's value. **`closedby="any"`** adds light dismiss (click outside) **[Frontier]**.

### The Popover API

`popover` (`auto` light-dismisses and closes other auto popovers, `manual` doesn't, `hint` for tooltips that don't close menus) plus **`popovertarget`** on a button makes a menu, tip or toast with no script. Popovers live in the top layer without modality. Style them with `:popover-open`, and animate entry and exit with **`@starting-style`** and `transition-behavior: allow-discrete`. Pair them with **anchor positioning** (Part 10) to attach them to their button.

### Invoker commands **[Frontier]**

**`commandfor`** + **`command`** wire a button to an element declaratively: `show-modal`, `close`, `request-close`, `toggle-popover`, `show-popover`, `hide-popover`, or your own `--custom` command that fires a `command` event. **`interestfor`** does the same for hover/focus interest (tooltips, link previews). Feature-detect and keep a fallback.

### Customisable `<select>` **[Frontier]**

Opt in with `appearance: base-select` on the select *and* its `::picker(select)`. Options can then contain rich content (icons, descriptions), the button shows the chosen option through `<selectedcontent>`, and every part is stylable. Engines without support render a normal select, so wrap the styling in `@supports (appearance: base-select)`: that is the progressive-enhancement story.

## Styling form controls

The quick win is **`accent-color`**: one line recolours checkboxes, radios, ranges and progress bars. **`color-scheme: light dark`** makes native controls follow dark mode. For full control, `appearance: none` on the input itself keeps the **native element** (focus, keyboard, form submission, accessibility) while you draw it; never hide the input and fake a checkbox with a `<div>`. Also `::file-selector-button`, `::placeholder` (keep it at contrast), and **focus styles** that meet WCAG 2.4.11/2.4.13 (a 2px solid ring with 3:1 contrast). Targets must be at least **24×24 CSS px** (WCAG 2.5.8); 44×44 is comfortable.

## File uploads in HTML

`<input type="file">` with `accept` (a hint, not a security check), `multiple` and `capture`, inside a `multipart/form-data` form, is the whole baseline. Drag-and-drop and instant previews are **enhancements** on top of the same input, so keyboard and screen-reader users keep the native picker. The server (Part 22) must re-check type by content, limit size, rename files and store them outside the web root.
