## What HTML actually is

HTML is a markup language **whose specification includes its own parser**. The WHATWG HTML Living Standard defines the elements, what they mean, the DOM they produce, and exactly how every malformed document is recovered. That last part is unusual: most languages reject bad input, but HTML has a precise, deterministic recovery for *every* possible byte sequence. "Invalid HTML still renders" is designed behaviour, not luck, and it is why two browsers build the same DOM from the same mess.

The practical consequence: you never get an error for broken markup. You get a *different document* from the one you meant. Paste something broken below and compare.

## What CSS actually is

CSS is a **declarative, rule-based language for assigning values to properties on boxes**. You never tell it *how* to lay things out step by step. You state constraints ("at least 16rem wide", "share the remaining space", "wrap when you must") and the layout algorithms resolve them. The shift from imperative thinking ("move this 20px left") to constraint thinking ("these items should be spaced evenly, whatever their count") is the first real lesson.

```css
/* Constraints, not instructions: the browser works out the columns. */
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(min(100%, 12rem), 1fr));
  gap: 1rem;
}
```

## The three trees

Keep three trees in your head:

- **The DOM**: what the parser built.
- **The box tree**: what CSS generates from the DOM. Some elements produce no box (`display: none`, `<head>`), some produce several (a list item and its `::marker`), and pseudo-elements add boxes the DOM never had.
- **The accessibility tree**: what assistive technology sees: roles, names, states. It is derived from the DOM plus ARIA plus *some* CSS (`display: none` removes nodes; `content` in pseudo-elements can contribute to names).

Almost every "works for me, broken for them" bug lives in the gap between two of these trees.

## The pipeline in one line

**bytes → tokens → DOM → style (cascade + computed values) → box tree → layout → paint → composite.** Each arrow is a stage your code can make expensive. Changing geometry re-runs layout and everything after it; changing a colour only repaints; changing `transform` or `opacity` can skip straight to compositing. The browser-engineering detail lives in L18 Part 1; here, learn to ask "which stage does this change hit?"

## How standards happen

- **WHATWG** writes the living standards for HTML, DOM, Fetch and URL. There are no versions, only the current text.
- **The W3C CSS Working Group** ships CSS as independent *modules* at *levels* (Selectors 4, Color 5, Cascade 6). There is no "CSS4".
- **Browser engines** (Blink, WebKit, Gecko) implement, publish standards positions, and run origin trials.
- **Baseline** says whether a feature works in all major engines (newly vs widely available). **Interop** is the yearly cross-browser project that fixes agreed focus areas: for 2026, anchor positioning, scroll-driven animations, view transitions and more.
- **caniuse** and MDN's compatibility tables are the day-to-day lookup.

## Your toolchain

A code editor with Emmet, a formatter (Prettier or Biome), **Stylelint**, the **Nu HTML Checker**, all three browser engines (Chrome, Firefox, and Safari or WebKit via Playwright), Firefox's grid and flex inspectors, a screen reader, a local static server with live reload, and Figma or Penpot for exploring designs.

```json
{
  "scripts": {
    "dev": "vite",
    "lint:css": "stylelint \"**/*.css\"",
    "format": "prettier --write .",
    "validate": "vnu --skip-non-html ."
  }
}
```

## Reading the sources that matter

Read **MDN** first. Read the **CSS specs** for mechanism: they are more readable than their reputation. Learn the property definition ("propdef") table: *initial value, applies to, inherited, percentages, computed value, animation type*. It answers most "why doesn't this work?" questions before you ask them. For HTML, each element's spec entry lists its **content categories**, **content model** and **permitted ARIA**. Supplement with the CSS-Tricks almanac and web.dev's *Learn HTML*, *Learn CSS* and *Learn Design*.

<Try task="Find the propdef table for `z-index`. Which row explains why `z-index` does nothing on a static element?">
  **Applies to: positioned elements** (plus flex and grid items, per the Positioned Layout and flexbox specs). A static, non-flex, non-grid element isn't in the "applies to" set, so the declaration is valid but inactive.
</Try>

## Where HTML and CSS end

HTML and CSS describe documents and presentation. Behaviour is JavaScript, data is the server, and design judgement is yours. But every year the platform moves behaviour *into* HTML and CSS: dialogs, popovers, invoker commands, exclusive accordions, carousels, scroll-driven animations, view transitions, anchored tooltips. The modern designer-developer reaches for the declarative version first and adds script only where the platform stops.
