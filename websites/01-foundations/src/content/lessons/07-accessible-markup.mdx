## The accessibility tree

Browsers build a second tree for assistive technology. Each node has a **role**, a **name**, a **description**, **states** (expanded, checked, disabled) and a **value**. It comes mostly from HTML semantics, then ARIA, and some CSS: `display: none` and `visibility: hidden` remove nodes; `content` in `::before`/`::after` contributes to names; `display: contents` historically dropped roles from some elements (buttons, tables); and **removing list styles drops list semantics in Safari** unless you add `role="list"`. Read it in DevTools (Elements → Accessibility, or the full-page tree view).

## Accessible name computation

The precedence: **`aria-labelledby`** → **`aria-label`** → the native label (`<label>`, `alt`, `<caption>`, `<legend>`, `<figcaption>`, SVG `<title>`) → **content** (for roles that allow it: buttons, links, headings, cells) → `title` (last resort, and not a real label). An icon-only button has no name until you give it one. And **label in name** (WCAG 2.5.3): the visible text must be part of the accessible name, so voice-control users can say "click Send" and have it work.

## The rules of ARIA

1. **Don't use ARIA if a native element exists.** `<button>`, not `<div role="button">`.
2. **Don't change native semantics** unless you must (`<h2 role="tab">` is wrong; put the tab inside the heading).
3. **Every interactive ARIA control must be keyboard-operable.**
4. **Never put `role="presentation"` or `aria-hidden="true"` on a focusable element**: keyboard users land on something that doesn't exist for screen readers.
5. **Every interactive element needs an accessible name.**

"No ARIA is better than bad ARIA": pages with ARIA average *more* accessibility errors than pages without, because each role is a promise.

## The ARIA vocabulary you'll actually use

- **Naming**: `aria-label`, `aria-labelledby`, `aria-describedby`.
- **State**: `aria-expanded` (+ `aria-controls`), `aria-pressed` (toggle buttons), `aria-selected` (tabs, options), `aria-checked`, `aria-current` (`page`, `step`, `date`), `aria-invalid` + `aria-errormessage`, `aria-busy`, `aria-haspopup`, `aria-sort`.
- **Live**: `aria-live="polite"`/`"assertive"`, `role="status"` (polite), `role="alert"` (assertive).
- **Structure fixes**: `aria-hidden="true"`, `role="list"`, `role="region"` (with a name).

Widget roles (`tab`, `listbox`, `menu`, `grid`, `tree`, `combobox`) come with full keyboard contracts: get them from native elements or a headless library (React Aria, Radix, Ark) rather than hand-rolling.

## APG patterns and keyboard models

The **ARIA Authoring Practices Guide** documents the expected keyboard model for each widget: **tabs** (one Tab stop for the list, arrow keys move between tabs, *roving tabindex*), **menu button**, **disclosure navigation** (usually better than an ARIA "menu" for site navigation, which is almost never `role="menu"`), **combobox**, **listbox**, **tree**, **grid**, **carousel** and **dialog**. Match the pattern exactly: screen-reader users expect it.

## Focus and keyboard

Tab order **follows DOM order**, so CSS reordering (`order`, grid placement, `row-reverse`, absolute positioning) can make it diverge from what people see; `reading-flow` **[Frontier]** is the emerging fix. Use `tabindex="0"` (add to the order) and `"-1"` (focusable by script) only; positive values create chaos. Give **`:focus-visible`** a clearly visible style (WCAG 2.4.7, 2.4.11, 2.4.13). Provide **skip links**. Make off-screen or background content **`inert`**. Stop sticky headers hiding the focused element with **`scroll-padding-top`**. And after dynamic changes (deleting a row, closing a dialog), **move focus somewhere sensible**.

## Hiding content correctly: three intents

| Intent | How | Effect |
| --- | --- | --- |
| Hidden from everyone | `hidden` attribute, `display: none` | Not rendered, not in the accessibility tree |
| Visible only to screen readers | the **visually-hidden** class | In the tree, zero pixels |
| Visible, but hidden from assistive technology | `aria-hidden="true"` | Rendered, not in the tree (decorative duplicates, icons beside text) |

```css
.visually-hidden:not(:focus):not(:active) {
  position: absolute;
  width: 1px;
  height: 1px;
  margin: -1px;
  padding: 0;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}
```

  `<button>Add to cart<span class="visually-hidden">: Trail Runner 3</span></button>`, or `aria-describedby` pointing at the product title. The visible text stays "Add to cart", the name becomes "Add to cart: Trail Runner 3", and 2.5.3 still passes because the visible text is at the start of the name.
</Try>

## CSS that affects accessibility

- **Contrast**: 4.5:1 for text, 3:1 for large text, UI component edges and focus indicators; **never colour alone** for meaning.
- **`prefers-reduced-motion`**, **`prefers-contrast`**, and **`forced-colors: active`** (Windows High Contrast: system colours replace yours, borders reappear, background images vanish; use `forced-color-adjust` sparingly and system colour keywords like `CanvasText`).
- **Text spacing** (1.4.12): layouts must survive line height 1.5, paragraph spacing 2×, letter spacing 0.12em and word spacing 0.16em.
- **Reflow at 320 CSS px** (1.4.10) and **resize text to 200%** (1.4.4): `px` font sizes and `vw`-only fluid type fail, so fluid type must include `rem`.
- Alt text for generated content: `content: "★" / "Rating"`.
- Content revealed on hover must be **dismissible, hoverable and persistent** (1.4.13).

## Target size, pointer cancellation and dragging

**Target size** (2.5.8): at least **24×24 CSS px** (or enough spacing around smaller targets); 44×44 is the comfortable norm. **Pointer cancellation** (2.5.2): actions fire on up-events (`click`), so people can slide off to cancel. **Dragging** (2.5.7) needs a single-pointer alternative (buttons to reorder, a click to place). **Consistent help** (3.2.6): help links in the same place on every page.

## Dynamic content and live regions

Screen readers don't see changes unless told. A **live region must exist in the DOM before its content changes**: render an empty `role="status"` (polite) or `role="alert"` (assertive, for errors only) on load, then update its text. Status messages (4.1.3) like "3 results" or "Saved" must be announced without moving focus. Use `aria-busy="true"` while a region loads. In single-page apps, **announce route changes** and move focus to the new `<h1>` or `<main>`.

## Testing your markup

Automated tools (**axe DevTools**, Lighthouse) catch perhaps a third of issues. The rest needs people: the DevTools **accessibility pane** and full-page tree, a **real screen reader** (VoiceOver with the rotor, NVDA in browse mode, TalkBack), a **keyboard-only** pass, **forced-colors emulation** (DevTools → Rendering), and **zoom to 400%**. Automate what you can in CI; every page of this site is checked with axe in its end-to-end test:

```ts
import AxeBuilder from '@axe-core/playwright';
import { expect, test } from '@playwright/test';

test('lesson page has no WCAG A/AA violations', async ({ page }) => {
  await page.goto('/learn/07-accessible-markup/');
  const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa', 'wcag22aa']).analyze();
  expect(results.violations).toEqual([]);
});
```
