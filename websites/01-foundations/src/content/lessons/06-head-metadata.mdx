## The minimal correct `<head>`, in order

1. **`<meta charset="utf-8">`**, first, within the first 1024 bytes.
2. **`<meta name="viewport" content="width=device-width, initial-scale=1">`**. Never `maximum-scale=1` or `user-scalable=no`: they break zoom and WCAG. Add `viewport-fit=cover` to draw under notches, and `interactive-widget=resizes-content` so on-screen keyboards resize the layout **[Frontier]**.
3. **`<title>`**.
4. Critical resource hints (preconnect, preload), then styles, then scripts (`defer` or `type="module"`).

Everything else (description, canonical, icons, social tags, JSON-LD) follows. The order matters because the browser acts on the first items while it's still parsing.

## Titles and descriptions are user-facing copy

`<title>` appears in tabs, bookmarks, history, search results and share cards, and **screen readers announce it on every navigation**. Make it unique per page, **front-load the distinctive part** ("Cycle lanes approved · The Daily Planet", not "The Daily Planet · News · Cycle lanes approved"), and keep it under ~60 characters. `<meta name="description">` is the snippet under the title in search results (~150–160 characters): write it as a pitch for this page, not a list of keywords.

<Try task="Rewrite these titles: 'Home', 'Products | ACME Corp | Best Quality Products Online', 'Untitled Document', and 'Blog - Post - 2026 - 09 - How we cut our build time in half'.">
  "ACME · Hand-thrown ceramics from Jaipur" (home, what makes it distinct); "Serving bowls · ACME" (a category page names the category first); a real title for the document, e.g. "Q3 hiring plan"; "How we cut our build time in half · ACME Engineering". Each is unique, starts with the words someone scanning tabs needs, and ends with the brand.
</Try>

## The `<link rel>` vocabulary

| `rel` | What it does |
| --- | --- |
| `stylesheet` | Render-blocking CSS |
| `icon`, `apple-touch-icon`, `manifest` | Icons and the web app manifest (Part 4) |
| **`canonical`** | The one URL that represents this content (deduplicates `?utm=` and `/index.html` variants) |
| `alternate` | Translations (`hreflang`), feeds (`type="application/atom+xml"`) |
| **`preload`** | Fetch a late-discovered critical resource now; needs the right `as` (and `crossorigin` for fonts) |
| `preconnect`, `dns-prefetch` | Warm up a connection to an origin you'll need soon |
| `modulepreload` | Fetch and parse an ES module ahead of time |
| `prefetch` | Low-priority fetch for a likely *next* navigation |
| `me`, `license`, `search` | Identity verification (IndieWeb, Mastodon), licensing, OpenSearch |

```html
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="preload" href="/fonts/fraunces.woff2" as="font" type="font/woff2" crossorigin>
<link rel="stylesheet" href="/styles/site.css">
<link rel="canonical" href="https://planet.example/news/cycle-lanes">
<link rel="alternate" hreflang="hi" href="https://planet.example/hi/news/cycle-lanes">
<link rel="alternate" type="application/atom+xml" title="Daily Planet news" href="/feed.xml">
<link rel="me" href="https://mastodon.social/@dailyplanet">
```

<Try task="Your hero image is set as a CSS background, so the preload scanner can't see it. Write the one line that fixes discovery, and say when you'd use preconnect instead.">
  `<link rel="preload" href="/img/hero.avif" as="image" type="image/avif" fetchpriority="high">` (use `imagesrcset`/`imagesizes` if it's responsive). Better still: make it an `<img>` so the scanner finds it. Use `preconnect` when you know the *origin* but not the exact URL yet (a font CDN, an image CDN), and only for one or two critical origins.
</Try>

## The `<meta>` vocabulary

- **`robots`**: `noindex`, `nofollow`, `max-image-preview:large`.
- **`color-scheme`**: `light dark` so the browser paints the right default canvas, text colour and form controls before CSS loads.
- **`theme-color`**, with `media="(prefers-color-scheme: dark)"` for a second value: colours browser UI on mobile.
- `referrer`, `format-detection` (`telephone=no` stops iOS turning numbers into links), `generator` (don't: it advertises your stack), and `http-equiv` (a CSP in a meta tag can't use `frame-ancestors` or reporting; prefer real headers).

## Social previews: Open Graph and Twitter cards

Share cards come from **Open Graph**: `og:title`, `og:description`, **`og:image`** (1200×630, absolute URL) with **`og:image:alt`**, `og:url`, `og:type` and `og:site_name`, plus `twitter:card="summary_large_image"`. Generate them **per route**, and render the image from HTML/CSS at build time (Satori, or a headless browser screenshot, Part 23). Social scrapers don't run JavaScript, so this must be server-rendered.

```html
<meta property="og:type" content="article">
<meta property="og:site_name" content="The Daily Planet">
<meta property="og:title" content="Cycle lanes approved">
<meta property="og:description" content="14 km of protected lanes by 2027. Here's what changes on your street.">
<meta property="og:url" content="https://planet.example/news/cycle-lanes">
<meta property="og:image" content="https://planet.example/og/cycle-lanes.png">
<meta property="og:image:width" content="1200">
<meta property="og:image:height" content="630">
<meta property="og:image:alt" content="Map of the city with the new cycle lanes in orange">
<meta name="twitter:card" content="summary_large_image">
```

## Structured data with JSON-LD

`<script type="application/ld+json">` holds **schema.org** data: `Article`/`BlogPosting`, `Product` (with `Offer` and `AggregateRating`), `BreadcrumbList`, `Organization`, `Person`, `Event`, `FAQPage`, `Recipe`. Search engines use it for rich results. **The honesty rule**: markup must match visible content. Validate with the Rich Results Test and the Schema Markup Validator.

## Speculation rules

`<script type="speculationrules">` tells the browser which navigations to **prefetch** or **prerender** ahead of time, by URL list or document rules with `eagerness` (`immediate`, `eager`, `moderate` on hover, `conservative` on pointer-down) **[Frontier]**. Prerendered pages run their JavaScript before the user arrives, so analytics and side effects must wait for `document.prerendering` to become false.

```html
<script type="speculationrules">
{
  "prerender": [{
    "where": { "and": [{ "href_matches": "/learn/*" }, { "not": { "selector_matches": "[rel~=nofollow]" } }] },
    "eagerness": "moderate"
  }]
}
</script>
<script>
  if (document.prerendering) {
    document.addEventListener('prerenderingchange', () => sendPageView(), { once: true });
  } else {
    sendPageView();
  }
</script>
```

<Try task="Which links on a store should you never prerender? Name three and why.">
  "Add to cart", "Log out" and "Delete" (anything with side effects on GET, which is itself a bug); links to huge pages that would waste data; and third-party links you can't control. Also avoid prerendering pages that start expensive work (video, websocket connections) before the user commits.
</Try>

## The web app manifest

A JSON file linked with `<link rel="manifest">`: `name`, `short_name`, **`icons`** (192 and 512, plus a **maskable** one), `display` (`standalone`, `minimal-ui`, `browser`), `theme_color`, `background_color` (the splash screen), `start_url`, `scope`, `id` and `shortcuts`. Installability details live in `L18-cs-web-engineering.md` Part 13.

```json
{
  "name": "The Daily Planet",
  "short_name": "Planet",
  "id": "/",
  "start_url": "/?source=pwa",
  "display": "standalone",
  "background_color": "#fbf8f5",
  "theme_color": "#c2410c",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icon-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ],
  "shortcuts": [{ "name": "Today's paper", "url": "/today" }]
}
```

<Try task="Open DevTools → Application → Manifest on any installable site. Which fields are missing or produce warnings?">
  Common findings: no maskable icon (Android shows a white circle around the logo), `short_name` too long for the home screen, missing `id` (the app's identity changes if `start_url` changes), and `theme_color` not matching the `theme-color` meta.
</Try>

## `lang` and `dir`

`<html lang="en">` sets the language for screen-reader **pronunciation**, CSS **hyphenation** (`hyphens: auto` only works with a language), **font selection** for shared code points (Han characters in Japanese vs Chinese fonts), spell-checking, quotes and translation tools. Mark inline foreign phrases too: `<i lang="fr">déjà vu</i>`. **`dir="rtl"`** sets right-to-left documents (Arabic, Hebrew, Urdu), and `dir="auto"` handles user content of unknown direction.

## Head management in frameworks

Every route needs its own title, description, canonical and social tags, rendered **on the server**, because social scrapers and some crawlers don't run JavaScript. React 19 **hoists** `<title>`, `<meta>` and `<link>` rendered anywhere in the tree into the head; Next.js has `metadata` exports; Astro and other SSG tools render the head per page from frontmatter (this site does exactly that).

```tsx
// React 19: rendered inside the component, hoisted into <head>
export function ArticlePage({ article }: { article: Article }) {
  return (
    <article>
      <title>{`${article.title} · The Daily Planet`}</title>
      <meta name="description" content={article.summary} />
      <link rel="canonical" href={`https://planet.example/news/${article.slug}`} />
      <h1>{article.title}</h1>
    </article>
  );
}
```

<Try task="View the source (not the DevTools DOM) of a single-page app you use. Is the title in the HTML the server sent? What does a share card for a deep link show?">
  If the served HTML has a generic `<title>` and no `og:` tags, every deep link shares as the home page and crawlers that don't execute JavaScript see nothing. The fix is server rendering or prerendering the head for each route.
</Try>
