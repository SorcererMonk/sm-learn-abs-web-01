## CSS is render-blocking

The browser won't paint until it has the CSSOM for every stylesheet that applies. So: keep critical CSS small, **inline critical CSS** for the first paint where it pays, load non-critical styles without blocking (a `media` attribute that doesn't match, or per-route splitting), **avoid `@import` chains** (serial waterfalls), and put stylesheets before scripts. This site inlines small stylesheets automatically and ships one bundled stylesheet per page.

```html
<head>
  <!-- 1. Critical CSS for the first screen, inline: no request needed -->
  <style>/* header, hero, type, colours: a few KB */</style>

  <!-- 2. Everything else, without blocking the first paint -->
  <link rel="stylesheet" href="/css/site.css" media="print" onload="this.media='all'">
  <noscript><link rel="stylesheet" href="/css/site.css"></noscript>

  <!-- A print stylesheet never blocks screen rendering -->
  <link rel="stylesheet" href="/css/print.css" media="print">
</head>

<!-- Avoid: a.css → @import b.css → @import c.css: three round trips before first paint -->
```

<Try task="In DevTools → Network, throttle to Slow 4G and reload any content site. How long is the gap between the HTML arriving and the first paint, and which stylesheet requests sit on the critical path?">
  Look at the waterfall: every `<link rel="stylesheet">` in the head (and anything they `@import`) must finish before First Contentful Paint. On slow connections that's often 1–3 seconds of blank screen. Inlining the few KB needed for the first screen and deferring the rest usually moves FCP to right after the HTML arrives.
</Try>

## Style recalculation cost

Recalculation cost is roughly **elements × rules that might match**. The usual problem is a **large DOM** (thousands of nodes; a common guideline is under ~1,500), not selector cleverness. Watch `:has()` and sibling-combinator invalidation on hot subtrees, avoid toggling classes on `<body>` in hot paths, and use DevTools' **selector stats** when recalculation shows up in traces.

## Layout cost and layout thrashing

Properties trigger different amounts of work: **layout** (geometry: `width`, `height`, `margin`, `padding`, `top`, `font-size`, `display`), **paint** (`color`, `background`, `box-shadow`, changing `border-radius`), or only **composite** (`transform`, `opacity`, some `filter`). **Forced synchronous layout** happens when you read geometry after writing styles; in a loop, that's **layout thrashing**. Batch all reads, then all writes.

## Containment and skipping work

`contain: layout | paint | size | inline-size | style | content | strict` promises what a subtree can't affect, so the browser can skip work. **`content-visibility: auto`** with `contain-intrinsic-size: auto 500px` skips rendering off-screen sections of long pages (big wins; test find-in-page, anchors and accessibility). `content-visibility: hidden` keeps cached off-screen views (tabs, routes) without the cost of rendering them.

## Compositing and layers

Elements can be promoted to their own **compositor layer** (transforms and opacity animations, `will-change`, video, canvas, fixed elements). Layers make animation cheap and memory expensive. **`will-change` is a hint, not magic**: add it just before an animation and remove it after. Many animated elements cause **layer explosion**; overlapping content can be promoted implicitly. Inspect with the Layers panel and "Layer borders" in the Rendering panel.

## Layout shift (CLS) from markup and CSS

Causes: images without dimensions, ads and embeds without reserved space, **web fonts swapping metrics** (fix with metric overrides, Part 14), content injected above existing content, animating layout properties, and scrollbars appearing (**`scrollbar-gutter: stable`**). Measure with the Layout Shift Regions overlay and the Performance panel's "Layout shifts" track.

## Paint-heavy styles

Large `box-shadow` blurs, `filter: blur()`, `backdrop-filter`, and big gradients on scrolling layers can be expensive to paint every frame. **Measure with paint flashing** (Rendering panel) and the Performance panel, not by folklore: many "expensive" effects are fine when static.

## CSS payload

Find **unused CSS** with the Coverage panel; remove duplication; minify and serve with **Brotli**; **split by route or component**; purge utility frameworks. CSS bytes are usually cheaper than JavaScript bytes, but they **block rendering**, so the first-screen CSS matters most.

<Try task="Open DevTools → Coverage (Ctrl/Cmd+Shift+P → 'Coverage'), reload this page, and read the CSS rows. What percentage of this page's CSS is unused, and why might that be acceptable here?">
  A lesson page loads the shared stylesheet, so rules for the home page, dojo, coverage table and other lessons' demos show as unused (often 50–70%). It's acceptable because the file is small, compressed, cached across every page after the first visit, and splitting it further would add requests. On a large app with a 300 KB stylesheet, the same number would justify route-level splitting.
</Try>

## DevTools mastery for CSS

Each browser has strengths. The **Styles** pane (toggle, edit, `:hov` state forcing, colour picker with contrast and gamut info, easing and shadow editors); **Computed** (the winning value and why); the box-model diagram; **flex and grid overlays**; **Firefox's inactive-CSS hints** and font panel; the **Changes** tab; **CSS Overview** (colours, fonts, unused declarations, media queries); the **Animations** panel (slow down, scrub); the **Rendering** panel (paint flashing, layout-shift regions, layer borders, emulate `prefers-*`, forced colours, vision deficiencies, print media, auto dark mode); the Accessibility pane; Recorder; and **Local Overrides** for testing CSS against production.

## Debugging CSS systematically

1. **Reproduce in isolation**: a reduced test case in a blank HTML file or a CodePen.
2. **Does the rule apply?** Selector matches? Which layer? Specificity? Valid value? Typos?
3. **Can the property apply?** Inactive properties: `z-index` on a static element, `width` on an inline, `justify-self` in flex.
4. **Which algorithm is in charge?** Flow, flex, grid, table, positioned.
5. **Containing block and formatting context?**
6. **Browser support?**

And the classic debug style: `* { outline: 1px solid red }`.

## Tooling

**Stylelint** (with ordering and token-enforcement rules), Prettier or Biome, **browserslist** as the shared target definition, **Lightning CSS** or PostCSS for lowering modern syntax, autoprefixer (mostly unnecessary now), bundler CSS handling (Vite, CSS Modules, code-split CSS), **Baseline** status in editors and linters, and `@supports` for feature detection.

```jsonc
// .stylelintrc.json: enforce the architecture, not just formatting
{
  "extends": ["stylelint-config-standard"],
  "rules": {
    "selector-max-id": 0,
    "max-nesting-depth": 3,
    "declaration-no-important": true,
    "color-no-hex": [true, { "message": "Use a colour token: var(--color-…)" }],
    "declaration-property-value-disallowed-list": {
      "/^(margin|padding|gap)/": ["/^\\d+px$/"]
    }
  }
}
```

  E.g. `selector-max-id: 0` (specificity wars), `declaration-no-important` (override chains), a disallowed-values rule forcing tokens for spacing and colour (47 greys). Browserslist: `"> 0.5%, last 2 versions, not dead"` or, stricter and Baseline-aligned, `"baseline widely available"`. Share it with Lightning CSS/PostCSS so syntax lowering matches the real audience.
</Try>

## Measuring what matters

**Lighthouse** for lab signals and regressions, the **Performance panel** for the truth about a frame, **WebPageTest** filmstrips for perceived loading, and **field data** (CrUX, RUM) for everything else (`L18-cs-web-engineering.md` Part 5). This site's end-to-end checks run Lighthouse on mobile settings and fail if performance drops below 90.

<Try task="Run Lighthouse (mobile, simulated throttling) on this page, then record a Performance trace with 4× CPU throttling while scrolling. Compare what each tells you.">
  Lighthouse gives a lab score, LCP, CLS and TBT under one simulated condition, plus opportunities (render-blocking resources, unused CSS). The trace shows what actually happens per frame: long tasks, style recalculation, layout and paint during scroll. Lab tools find regressions; only field data from real users tells you what they experience.
</Try>
