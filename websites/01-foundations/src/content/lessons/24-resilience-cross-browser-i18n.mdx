## Progressive enhancement as layered design

Core **content and function in HTML** → **presentation in CSS** with fallbacks → **behaviour in JavaScript**. "Cutting the mustard": a feature test decides whether to load the enhanced experience at all. And remember: **every user is on the no-JS path** while JavaScript loads, and some stay there when it fails.

## Fallbacks in CSS

**Declaration repetition** (older value first, modern one second), **`@supports`** feature queries (`@supports (anchor-name: --a)`, `@supports selector(:has(a))`, `@supports not (…)`), `var()` fallbacks, `min()`/`max()` fallbacks. The trap: **one unsupported selector in a list invalidates the whole rule**, so use the forgiving `:is()` or separate rules.

## Cross-browser realities

Three engines: **Blink** (Chrome, Edge, Opera, Samsung), **WebKit** (Safari, and every iOS browser in most regions), **Gecko** (Firefox). **Safari/iOS is the special case**: viewport quirks, the virtual keyboard, `position: fixed` behaviour, form-control styling, and release cycles tied to OS updates. Drive your testing matrix from **analytics**, test on **real devices** as well as emulation (BrowserStack, Sauce Labs), and read the **Interop dashboard** and caniuse critically (partial support notes matter).

## Defensive CSS

Ahmad Shadeed's catalogue and beyond: long words and URLs (`overflow-wrap: anywhere`), long names in flex items (**`min-width: 0`**), images without dimensions (`object-fit`), `flex-wrap` on anything that might wrap, **`minmax(0, 1fr)`**, scrollbar gutters, `max-width: 100%` on media, background images with a fallback colour, button text that might grow, vertical centring that survives two lines, spacing that survives missing elements (`gap` over margins, `:empty`), `auto-fit` vs `auto-fill`, and sticky/overflow conflicts.

## Content stress-testing

Test with the **real extremes**: empty, one character, 400 characters, very long names, user images of any aspect ratio, **0, 1 and 1,000,000 items**, translations 30–40% longer (German, Finnish) or much shorter (Chinese), and larger user font sizes. **Pseudo-localisation** (accented, padded strings) finds all of these before translators do.

## Internationalisation in markup and styles

Correct **`lang`** at the document and phrase level; `dir="rtl"` and **`dir="auto"`** for user content; **`<bdi>`** to isolate names; logical properties everywhere; **mirror directional icons** (arrows, progress, "back") but not others (media controls, clocks, checkmarks), with `:dir(rtl)` for exceptions; text expansion; script-appropriate fonts and line heights; vertical writing modes; numbers, dates and currency formatted by **`Intl`** and rendered into `<time>` and `<data>`; and pseudo-localisation for testing.

## User preferences and overrides

Your CSS runs **on the user's terms**: user stylesheets, **minimum font sizes**, text-only zoom, reader mode, high-contrast themes and **forced colours**, reduced motion, reduced transparency, and extensions that rewrite pages (dark-mode extensions, translators, ad blockers).

## Testing HTML and CSS

**HTML validation** in CI (the Nu checker); **accessibility checks** (axe with Playwright); **visual regression** (Playwright screenshots, Chromatic, Percy, BackstopJS) across widths, themes and locales, with a strategy for font and animation nondeterminism; component stories as fixtures; **cross-browser runs** with Playwright's three engines; **link checking**; and **Lighthouse CI** for regressions. This site runs axe, a console-error check and a link crawl on every page in its end-to-end suite.

```ts
// playwright.config.ts: three engines × two themes, animations off for stable screenshots
import { defineConfig, devices } from '@playwright/test';
export default defineConfig({
  use: { baseURL: 'http://localhost:4321', reducedMotion: 'reduce' },
  projects: [
    { name: 'chromium-light', use: { ...devices['Desktop Chrome'], colorScheme: 'light' } },
    { name: 'webkit-dark', use: { ...devices['iPhone 15'], colorScheme: 'dark' } },
    { name: 'firefox-light', use: { ...devices['Desktop Firefox'], colorScheme: 'light' } },
  ],
});

// card.spec.ts
test('card survives hostile content', async ({ page }) => {
  await page.goto('/fixtures/card?name=long&locale=de&rtl=1');
  await page.evaluate(() => document.fonts.ready);
  await expect(page.locator('.card')).toHaveScreenshot({ maxDiffPixelRatio: 0.01 });
  const axe = await new AxeBuilder({ page }).include('.card').analyze();
  expect(axe.violations).toEqual([]);
});
```

## Browser support policy

Define it with **browserslist** and **Baseline** ("widely available" as the default bar; "newly available" with fallbacks), **document** it, and revisit it yearly. "Supports" can mean **identical**, **functionally equivalent** or **content-accessible**; pick one per browser tier.

```text
Browser support policy (reviewed September 2026)
Tier 1, identical experience: Baseline widely available (last 30 months of Chrome, Edge, Firefox, Safari)
Tier 2, functionally equivalent: Baseline newly available features ship behind @supports with fallbacks
Tier 3, content-accessible: any browser that parses HTML gets the content and working forms, unstyled if need be
browserslist: "baseline widely available, not dead"
```

<Try task="Write a support policy for a product whose analytics show 70% Chrome, 20% Safari iOS 17+, 6% Firefox, 3% Samsung Internet and 1% old Android WebViews. Which features from this course would you ship without a fallback?">
  Tier 1 (identical): current Chrome, Safari iOS 17+, Firefox, Samsung Internet. Tier 3 (content-accessible): old WebViews. Without fallbacks: grid and subgrid, container queries, `:has()`, `clamp()`, logical properties, `aspect-ratio`, `<dialog>`, cascade layers (all Baseline widely available). Behind `@supports` with fallbacks: anchor positioning, scroll-driven animations, customisable select, `interestfor`, `text-box-trim`. Revisit next September.
