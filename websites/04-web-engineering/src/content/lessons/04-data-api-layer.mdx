checks:
  - q: "Explain why session cookies are usually preferable to `localStorage` tokens, and the XSS and CSRF consequences of each."
    a: "An `HttpOnly; Secure; SameSite=Lax` session cookie can't be read by JavaScript, so XSS can't steal it. XSS can still act as the user while the page is open (so XSS is still critical), but the attacker can't take the credential away and replay it later from elsewhere. The session is server-side, so it can be revoked instantly. The cost is CSRF: the browser attaches cookies automatically, so you need SameSite plus a CSRF token or Origin check on state-changing requests. A token in `localStorage` is immune to CSRF (it's only sent when your code attaches it), but any XSS or any compromised third-party script can read it and exfiltrate it, and a stateless JWT usually can't be revoked before it expires. The auth lab shows `document.cookie` failing to see the session."
  - q: "Design optimistic updates for a 'like' button that behaves correctly under double taps, offline and server rejection."
    a: "Keep two pieces of state: the last server-confirmed value and the user's desired value. On tap, flip the displayed value immediately (with a subtle pending style), set desired, and send the desired state (`PUT {liked: true}`), not a toggle, so the operation is idempotent. If a request is in flight, don't send another: when it returns, send again only if desired differs from confirmed (double taps coalesce to the final intent). On failure (offline, 5xx, 403), roll back the display to the confirmed value and tell the user, with a retry action. If you're offline, queue the desired state in an outbox and replay it when back online. Reconcile with the server's returned count rather than trusting the local arithmetic. The optimistic lab implements exactly this."
  - q: "Explain the caching semantics of `stale-while-revalidate` at both the HTTP and the query-cache layer."
    a: "HTTP: `Cache-Control: max-age=60, stale-while-revalidate=300` means fresh for 60 s; for the next 300 s the cache may serve the stale response immediately while revalidating in the background (a conditional request with the ETag), so the next user gets the fresh copy; after that the cache must wait for the network. The browser cache and CDNs implement it. Query cache: `staleTime` plays max-age. Reads within it are served from memory with no request; after it, a read returns the cached data at once and triggers a background refetch, and subscribers update when it lands. Invalidation after a mutation makes it stale immediately. Both trade a little staleness for instant responses; set the windows per resource by how wrong stale data is allowed to be."

## API styles from the client's perspective

The main API styles, as the client experiences them:

- **REST**: resources with URLs, so **HTTP caching** works (`Cache-Control`, ETags, CDNs) and it is simple to debug. It can over-fetch, or need several round trips.
- **GraphQL**: client-shaped queries fetch exactly the fields needed in one round trip. Caching gets harder (one POST URL), and resolvers invite **N+1** queries on the server.
- **RPC-style typed endpoints** (tRPC and friends): type safety end to end without a schema layer, when the client and server ship together.
- **Server functions/actions** in meta-frameworks: RPC generated from colocated code.

The trade-offs are caching, versioning and tooling. Below, the same data three ways, served by this site's server. Its GraphQL endpoint is a 100-line implementation you can read.

## Client-side data caching

**Query caches** (TanStack Query, SWR, and their equivalents) hold server data under **cache keys**. They give you:

- **stale-while-revalidate** semantics: show the cache, refetch in the background;
- **deduplication** of in-flight requests;
- **background refetching** on focus or reconnect;
- a **retry policy**;
- **invalidation** after mutations;
- **pagination** and **infinite queries**.

That is why a query cache beats a hand-rolled store for server data: it already solves the invalidation you would otherwise write by hand, badly.

## Normalisation

A **normalised cache** (Apollo, Relay, RTK Query entities) stores each entity once by type and ID, so editing a user's name updates every screen that shows them. It earns its complexity for **heavily relational data edited in many places**. For most apps, **document-shaped caching** (each query's response as-is) plus invalidation is enough.

## Optimistic updates

**Optimistic updates** apply the change locally at once, then reconcile with the server's response, and **roll back on failure**. Handle **conflicts**: last write wins, or refuse with `412 Precondition Failed` via `If-Match` (the todos API does this). Make the **pending state visible** rather than invisible: a dimmed item, a "saving…" label, and never a silent revert.

## Real-time

Real-time options, and what each demands:

- **WebSocket** connection management:
  - reconnection with jittered backoff;
  - heartbeats: the socket can look open while dead;
  - auth on connect: the handshake sends cookies, so check the Origin;
  - message ordering: sequence numbers;
  - back-pressure.
- **SSE** for one-way streams.
- **Polling** as an honest fallback.
- **Presence** and **collaborative editing**: CRDTs, `L18-cs-fundamentals.md` Part 14.
- **Reconciling live updates with the query cache**: write events into the cache, not a second store.

This lab's WebSocket server is written from scratch on raw sockets (`server/core/websocket.ts`), so you can read the whole protocol.

## Offline and PWA data

Offline data has four pieces:

- **IndexedDB** as the local store;
- an **outbox** for mutations queued while offline, replayed idempotently by client-generated IDs;
- **Background Sync** where supported (Chromium), to replay even after the tab closes;
- **conflict resolution**: last-write-wins, server-wins with a merge UI, or CRDTs.

Be realistic about the web's limits compared with native (`L18-cs-app-engineering.md` Part 4): storage can be evicted, background time is short, and iOS support is narrower.

## Forms, done well

The checklist for a form done well:

- **Progressive enhancement**: it works without JavaScript.
- **One validation schema** shared by client and server.
- **Errors**: field-level and form-level, with **focus moved** to an error summary.
- **Submission states**, and **idempotent submits** so double clicks are harmless.
- **File uploads**: chunked and **resumable**, with **progress**, **direct-to-storage signed URLs**, and type checks **by content**.
- **Multi-step flows** that resume where the user left off.

## Streaming and large payloads

For large payloads:

- **Streamed HTML** and **streamed JSON** (NDJSON) show the first rows immediately.
- **Range requests** fetch part of a file (`Range: bytes=0-1023`, answered with `206`); this server supports them for every static file.
- **Paginate** instead of "load everything".
- **Virtualise** long lists: render only what's visible.

## Authentication in the browser

Authentication, in the browser:

- **Session cookies** (`HttpOnly`, `Secure`, `SameSite`) versus tokens in JavaScript-accessible storage. The former is the default recommendation.
- **Refresh strategies** and silent renewal.
- **OAuth 2.1/OIDC with PKCE** for third-party identity.
- **Passkeys/WebAuthn** as the modern primary factor.
- **Session fixation** defence: rotate the ID on login.
- **Logout across tabs** (`BroadcastChannel`, storage events), and **multi-tab consistency**.

```ts
// server/features/auth.ts: the whole login, minus logging
const session = requireCsrf(ctx, current(ctx));          // synchroniser token + Origin check
const gate = lockout.peek(email);                        // per-account token bucket
if (!gate.allowed) throw new HttpError(429, 'Too many attempts…', rateLimitHeaders(gate, 5));
const ok = verifyPassword(password, user?.passwordHash ?? DUMMY_HASH) && Boolean(user); // same time either way
if (!ok) throw new HttpError(401, 'Email or password is incorrect');                    // same message either way
const fresh = store.rotate(session, user.id);            // new ID: a planted pre-login ID is now useless
setCookie(ctx, fresh);                                   // HttpOnly; SameSite=Lax; Secure over HTTPS
```

## Authorisation on the client

**Client checks are UX only; server checks are security.** Hide what the user can't do (less noise). Disable what they could do after some change, and say why. Remove only what they must never know exists. **Feature flags** are not permissions: a flag decides whether a feature exists for a cohort, a permission decides whether this user may do this thing. Enforce permissions on every request, on the server.

## Error handling and resilience

Resilience, end to end:

- **Error boundaries** per route and per widget, so one failing panel doesn't blank the page.
- **Retry with backoff and jitter** for idempotent reads.
- **Tell failures apart**: offline, server error, rate limiting and validation errors each need a different response.
- **A user-visible recovery action** for every failure.
- **Telemetry on every failure path**, with the request ID (Part 12).
