## The platform's defining constraints

You ship to an **unknown device** (a four-year-old Android as often as a new laptop) over an **unknown network** (fibre, hotel Wi-Fi, a train tunnel) into an **untrusted runtime you do not control** (a browser with extensions, other tabs, and a user who can open DevTools). There is **no install step**, so every cold visit downloads your application; **no version pinning**, so every deploy reaches everyone at once; and a **decades-long backward-compatibility guarantee**: pages from 1996 still render, and yours will too if you stay on the standards.

## The four surfaces of every web application

Every web application lives on four surfaces:

- **Client**: a browser running your code in a sandbox, on one main thread shared with rendering and input.
- **Network**: latency, packet loss, caches and CDNs between the user and you.
- **Server**: rendering, APIs and data.
- **Build**: what you compile, bundle, hash and ship.

Most decisions trade one surface against another. Server-side rendering moves work from the client to the server. A CDN moves the server closer through the network. Code splitting trades one big download for more requests. Inlining CSS trades cacheability for one fewer round trip.

This page loaded through all four, and the browser recorded where the time went: the **Navigation Timing** API for the network and client phases, and the server's own **`Server-Timing`** header for its share.

## The web's unique properties

These properties shape everything else:

- **The URL is shareable application state.**
- **The back button is a user-owned undo.** Break it and you break trust.
- **View-source is permanent.** Assume every client-side secret is public.
- **Linkability and crawlability**: anything with a URL can be linked, indexed and previewed.
- **"The user agent is the user's, not yours."** Users zoom, block scripts, translate pages, override fonts and colours, and use assistive technology, and the page must survive all of it.

## Where the web wins and where it loses against native

The web wins on **reach** (one URL works on every device with a browser), **zero install** (no store, no download gate), **instant updates** (deploy once, everyone has it) and **linkability** (any state can be shared and indexed). It loses on **device integration** (Bluetooth, NFC and background sensors are partial or missing, especially on iOS), **background execution** (a closed tab stops running; background sync and push are limited), and the **performance ceiling** (heavy 3D, real-time audio and large offline datasets hit memory and thread limits first). Part 13 turns this into a decision framework.

| Need | Web | Native |
| --- | --- | --- |
| Reach from a shared link | Instant | Store detour |
| Ship a fix | Seconds, to everyone | Review, then user updates |
| Run while closed | Push and sync only, limited | Background tasks |
| Device APIs | Growing, uneven by browser | Full |
| Indexable content | Yes | No |

<Try task="Pick three apps on your phone. For each, decide web, native or both using the table above, and name the single capability that decides it.">
  Examples: a newspaper is web-first (reach, indexable content, instant updates) with an optional native wrapper for push. A step counter is native (it needs background sensors and runs while closed). A banking app is often both: a responsive web app for reach and accessibility, and a native app for biometrics, device binding and push. The deciding capability is usually background execution or a specific device API. If nothing on the "native" side is essential, the web's reach and zero install win.

## The failure modes this discipline exists to prevent

This course exists to prevent a set of engineering failures:

- multi-megabyte bundles shipped to phones;
- layouts that jump while loading;
- keyboard-inaccessible interfaces;
- cache-invalidation bugs that serve last week's JavaScript;
- auth implemented with tokens in `localStorage`;
- a single vendor script that owns your main thread.

## The composition of the discipline

The course is built in layers:

- **Platform knowledge**: Parts 1–2.
- **Architecture**: Parts 3–4.
- **The quality attributes the web cares most about**: Parts 5–8 (performance, accessibility, security, discoverability).
- **The server and delivery**: Parts 9–12.
- **The web as an app platform**: Part 13.
- **Judgement**: Part 14, the craft that turns all of the above into taste.

| Part | Mostly about | Surface |
| --- | --- | --- |
| 1 Browser runtime, 2 Platform APIs | how the client works | client |
| 3 Architecture, 4 Data & API | who renders, where state lives | client + server |
| 5 Performance | bytes, round trips, main-thread time | all four |
| 6 Accessibility, 8 Discoverability | the tree you ship to people and crawlers | client (HTML) |
| 7 Security | origins, cookies, headers, dependencies | client + server + build |
| 9 Server, 12 Delivery | caching layers, releases, observability | server + network |
| 10 Build, 11 Testing | what you ship and how you know it works | build |
| 13 PWA | offline, install, push | client + network |
