    a: "Hydration reuses server HTML by re-running the components on the client and attaching to the existing DOM; if the client's first render differs from the server's HTML, the framework reports a mismatch and patches or re-renders that subtree (throwing away work and sometimes causing flicker or lost input). Causes: rendering `Date.now()`/`new Date()` or `Math.random()`, locale or time-zone differences (`toLocaleString` on a UTC server versus the user's browser), reading `window`/`localStorage` during render, and invalid HTML nesting that the parser rewrote (a `<div>` inside a `<p>`).     a: "In the network panel a waterfall looks like a staircase: request B starts exactly when A ends, then C when B ends, usually because each component fetches in an effect after its parent rendered with data. ## Rendering strategies

Each strategy decides who does the rendering work, and when:

| Strategy | What it trades |
| --- | --- |
| **Client-side rendering** | Fast deploys and cheap servers, for a slow first paint (download, run, fetch, then render) and poor crawlability. |
| **Server-side rendering** | Fast first paint, for per-request server cost and the **hydration tax**. |
| **Static generation** | Cheapest and fastest, for **staleness**. |
| **Incremental / on-demand revalidation** | Static speed with bounded staleness. |
| **Streaming SSR** | Send the shell now, stream the slow parts as they resolve. |
| **Islands** | Ship JavaScript only for interactive regions. |
| **React Server Components** | Components that render on the server and never reach the client bundle. |
| **Resumability** (Qwik) | Serialise enough state that the client resumes instead of re-running. |
| **Edge rendering** | Close to the user, in a limited runtime. |

## Hydration

**Hydration** means the client re-executes the components the server already rendered, rebuilding their state and attaching event handlers to the existing DOM. Until it finishes, the page *looks* ready but isn't. That is why "time to interactive" and **INP** diverge from first paint, and why a heavy bundle hurts even with perfect SSR.

A **hydration mismatch** happens when the client's first render differs from the server HTML: dates, random IDs, locale, `window` checks, invalid nesting. The mitigations:

- **partial** and **progressive** hydration: some components, or later;
- **selective hydration on interaction**: hydrate what the user touches first;
- **event replay**: queue early clicks.

## Choosing per route, not per application

Rendering is chosen per route:

- **Marketing pages**: static.
- **Dashboards**: client-rendered behind auth, or SSR shell plus client navigation.
- **Content**: static with revalidation, or streamed.
- **Checkout**: server-rendered forms with enhancement.

## Routing architecture

A router's responsibilities:

- **URL as state**: path for resources (`/products/2`), query for filters (`?sort=price`).
- **Nested layouts** that persist across navigations.
- **Route-level data loading**: parallel where possible, dependent where necessary.
- **Prefetching** on hover, focus or viewport.
- **View transitions** between routes.
- **Scroll restoration** and correct **back/forward** semantics.
- **Deep-link correctness**: every URL loads directly, with the server returning the app for it.
- For SPAs, **focus management and announcement** on every route change.

## The state taxonomy

The five kinds of state, and where each belongs:

| Kind | Examples | Lives in |
| --- | --- | --- |
| **Server-cache state** | data you fetched | a query cache with staleness rules, not a global store |
| **URL state** | filters, tabs, pagination | the URL: shareable and restorable |
| **Client state** | auth session, theme, feature flags | app-wide client state |
| **Form state** | draft values, validation, submission status | the form |
| **Ephemeral UI state** | open menus, hover, focus | the component, or CSS |

Most "state management is hard" pain comes from putting server-cache state into a global store and then hand-writing cache invalidation.

## Data-fetching patterns

Data-fetching patterns, and the traps they avoid:

- **Colocate** queries with the components that use them, but **start** them at the route level.
- **Request waterfalls** show up in the network panel as staircases. The cure is to **load in parallel** and **preload** at the route level.
- **Suspense-style loading boundaries** keep the page from becoming a patchwork of spinners.
- **Pagination and infinite lists** need their position in the URL.
- **The frontend N+1 problem**: one request per list item, the twin of the server's N+1 query. Fix it with a batch endpoint or a BFF.

## Component architecture

Principles for components:

- **Composition over configuration**: children and slots, not 30 props.
- **Presentational versus container**: in modern form, hooks or loaders for data, components for markup.
- **Passing data down**: prop drilling, then context, then a store, in that order.
- **Controlled versus uncontrolled** components.
- **A clear boundary with the design system** (`L18-cs-design-engineering.md`).
- **Dependency direction rules**: features may import from shared, never from each other.

## Codebase structure

How to organise the code:

- **Feature-first folders** (`features/checkout/`, not `components/`, `hooks/`, `utils/`), plus a small **shared kernel** of UI, lib and types.
- **Module boundaries enforced by tooling**: lint rules like `no-restricted-imports` or eslint-plugin-boundaries, or package boundaries.
- **Monorepo layout**: `apps/`, `packages/`, `tooling/`.
- **Extract a package** when two apps need it, or when a boundary needs enforcing, not before.

```js
// eslint.config.js: features may use shared code, never each other's internals
export default [{
  files: ['src/features/**'],
  rules: {
    'no-restricted-imports': ['error', { patterns: [
      { group: ['../*/**', '!../shared/**'], message: 'Import other features through their public index.' },
    ] }],
  },
}];
```

## Micro-frontends

**Micro-frontends** mean splitting one product's frontend into independently deployed pieces owned by different teams: module federation, import maps, iframes, or edge composition. Weigh the real costs:

- duplicated runtimes (two Reacts, two design-system versions);
- **version skew**;
- shared-state hacks;
- an inconsistent design;
- debugging across boundaries.

The honest rule: they solve an **organisational** problem for large multi-team products, and create problems for everyone else.

## Framework-agnostic principles worth carrying

Principles that outlive any framework:

- **Unidirectional data flow**.
- **Derived state over duplicated state**: compute, don't copy.
- **Immutable updates**, so change detection is cheap and correct.
- **Stable identity for lists**: keys from data, not indexes.
- **Effects as synchronisation**, not lifecycle hooks: "keep X in sync with Y".
- **Make wrong states impossible to hold** (`L18-cs-software-engineering.md` Part 3).
